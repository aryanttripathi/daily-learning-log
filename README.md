# Daily Learning Log

A daily technical learning log that goes deep. Each entry targets the actual mechanics of a system (storage layouts, wire protocols, scheduler behaviour, failure modes) rather than a feature tour or a summary of marketing pages.

Every lesson is written to be *runnable*: it carries a hands-on exercise you can execute against a real system, at least one structural diagram of the mechanism under discussion, and a source list containing only links that were actually read while writing it.

## How This Works

- **One subject at a time.** The log follows a multi-week *track*: a sequential deep dive into a single database or systems subject. The track's syllabus and progress live in [`TRACK.md`](TRACK.md), which is the single source of truth for what has been taught and what comes next. For a long track, the append-only registers — PR candidates found along the way, and the ledger of open questions with the lesson that owns each — live beside it under [`tracks/`](tracks/); the JanusGraph track's are in [`tracks/janusgraph-registers.md`](tracks/janusgraph-registers.md).
- **One lesson per day, each building on the last.** Every day takes the first unchecked lesson from the syllabus. Lessons assume everything earlier in the track is known and open with a *Where This Fits* section linking the previous lesson. Missed days are never backfilled; the track simply continues.
- **Scope is handed forward explicitly.** A comment block in `TRACK.md` records, per lesson, what it took, what it deliberately left for a later lesson, which source commit it read, which measurements reproduced, and which did not. That is what keeps a long sequence from re-teaching itself or quietly contradicting an earlier day. `TRACK.md` keeps the notes for the three most recent lessons; older ones roll off into git history, and [`TRACK-ARCHIVE.md`](TRACK-ARCHIVE.md) records the exact commit and blob to read for each lesson range. Nothing is deleted and nothing is duplicated — the lesson documents themselves are the real record.

  A note records what that run *believed*, which is why the corrections are worth keeping a list of. On 2026-10-24 lesson 05 found that lesson 04's handover had confidently asserted an identifier that exists in no branch of PostgreSQL, so a specific claim is worth one fetch to check before building on it. On 2026-10-26 the correction ran the other way, against a *measurement* — lesson 06's "59 heap fetches" turned out to be `rows-on-the-dirtied-block + 1` and reproduced as 58. On 2026-11-04 a third kind: lesson 05's handover had described the in-memory backend as "unordered", and `InMemoryStoreManager` declares **both** scan shapes, so a loose adjective in a note is worth one re-read too. On 2026-11-07 a fourth: lesson 08's handover said `count == 0` is unreachable because `addPadding` forbids it, which is true but is the *second* line of defence — `BASE_ID = 1` means the id authority never offers a zero count at all. A correct claim can still be the wrong reason. On 2026-11-08 a fifth, and the most useful kind: two lessons had *accounted* for `TYPE_LEN_RESERVE` and `MAX_PADDING_BITWIDTH` without spending them, and a note that says "owed to lesson N" is what made the third lesson go looking. On 2026-11-09 a sixth, against an *explanation* rather than a fact: two lessons had recorded that the tail ids of a column are written backward *so that a parse can walk in from the end*, which is true and is not the reason — the backward encoding is the only order-preserving one in the package, and the tail is written that way so it can be used as a sort key. On 2026-11-11 a seventh, which closed a debt rather than correcting one: three separate lessons had written down *obligations* for lesson 13, and all three were discharged in one reading. On 2026-11-12 an eighth, the plainest kind: lesson 13's note had listed `attributes.custom.*` as a `FIXED` option, and it is `GLOBAL_OFFLINE`. On 2026-11-14 a ninth, and it is about a mechanism's *layer* rather than its content: lesson 15 had recorded that a property write's `upsert` flag "promises the commit path that a later delete must read the database", and lesson 16 found that the commit path never reads the flag at all — its single consumer is `StandardVertexProperty.remove()`, one layer up. A handover note is not only a correction channel; it is what makes a lesson arrive with questions instead of a blank page.
- **A separate Daily Diff digest every day.** Alongside the lesson, each day folder has a `daily-diff.md` covering an edition of [The Daily Diff](https://tdd.cat/): a point-wise summary plus a deep dive on the single most significant item, with its source link followed and the underlying thing read. A digest covers the newest edition not yet covered, says which one it is, and records how it was found. When no new edition has published, the digest says so explicitly rather than inventing items.

  **tdd.cat's endpoints are independently cached and disagree with each other, and twenty-nine consecutive runs produced twenty-nine different lead/lag patterns.** The front page, [`/md`](https://tdd.cat/md), the dated `https://tdd.cat/{YYYY-MM-DD}.md` permalink, the dated `https://tdd.cat/{YYYY-MM-DD}/` page, [`/archive/`](https://tdd.cat/archive/), [RSS](https://tdd.cat/rss.xml) and the per-edition PDF have each been observed leading, lagging, failing or disagreeing while the others worked. **The procedure, as it stands after the 2026-11-13 amendment:**

  1. Fetch the front page and [`/archive/`](https://tdd.cat/archive/) and take the **maximum** date either names. A *larger* archive maximum is a reason to probe that date; a *smaller* one is no reason to doubt the front page (2026-11-05).
  2. **Then probe `https://tdd.cat/{today}/` and `https://tdd.cat/{yesterday}/` directly**, because a published edition can be absent from *both* indexes while they agree with each other (2026-11-13). Try the no-slash form too — the trailing slash is part of the cache key and the two forms have disagreed in one run (2026-10-28).
  3. **Check the `TRACK.md` session log in both directions** before concluding anything: a floor, so a run does not re-digest the edition the previous entry covered (2026-11-07), and a ceiling, so it does not skip an uncovered one by invoking the fallback mechanically (2026-11-09).
  4. **Fallback, last resort only:** if the newest available edition is one a previous entry already digested and no newer edition exists, state the gap with timestamps and endpoints checked, then go deep on **one item from that edition the previous digest did not cover**, saying in the document that that is what is happening (2026-11-08).
  5. Identify editions by **date**, never by the archive's edition number, which has been observed moving backwards. Take the item count from the endpoint you took the items from and say which one that was — the HTML and PDF renderings of one edition have disagreed 43 against 33 (2026-10-24). Edition size carries no information about completeness (2026-11-10). A large edition's page can exceed the ~100 KB one WebFetch returns, so its tail needs a second call with an offset (2026-11-11, used for real on 2026-11-13).

  **There is no leader endpoint and no usable negative signal.** Every rule of the form "poll X first" has been killed on its first or second test, and a `client_error` on a dated page is a statement about one minute, not about whether the edition exists or will. The first-party explanation, found 2026-10-24, predicts the whole pattern: the front page states that *"Editions are published with a 2-day settling window so the highest-signal discussions and insights surface"* — so the front page and archive surface the *settled* view while RSS and the dated permalinks can expose an edition before it has settled.

- **Tracks end with a capstone.** When every lesson is checked, that day's document is a capstone assembling the whole system end to end. The subject moves to *Completed Subjects* in `TRACK.md`, and a new track begins.
- **Some tracks are reading sessions, not lessons.** A track whose `mode` is `contributor-reading` targets a codebase the reader intends to contribute to. Those entries do not explain the code; they point at the exact files to open at a pinned commit, give the minimum map needed to read them efficiently, pose questions whose answers are in the code, and list live upstream issues the reading touches. The other half of each entry is a **`## My Notes`** section written by the reader, and the next session opens by answering the open questions left there. An entry whose `My Notes` stays empty did not count, and the next run says so. **A track can change mode mid-flight**, and the JanusGraph track did on 2026-11-03: a reading-session track whose `My Notes` stays empty for several consecutive sessions is generating guides nobody reads, so the mode flips to `lesson` and the entries start answering their own questions. Entries keep whatever shape they shipped with; the mode only governs what comes next.

**What the track has established so far.** Session 01 set the premise the other 27 depend on: a vertex is a **row**, its incident edges and properties are that row's **cells sorted by column**, each edge is stored **twice** (once per endpoint row), and the maximum cells per row in a backend is therefore the maximum vertex degree JanusGraph can support on it — the supernode problem is a line of the data model, not a bug. Session 02 opened the contract those rows are read through: the column interval is **half-open**, `[sliceStart, sliceEnd)`; a `mutate` applies its **deletions strictly before its additions**; a lock taken with `acquireLock` is **only verified on the transaction's first `mutate`**. Session 03 read the 24 booleans a backend declares about itself and found that **nothing in the codebase verifies any of them** — the single enforcement point is one `checkArgument` in `OrderedKeyValueStoreManagerAdapter`'s constructor, and `Backend` reads locking *inverted*, wrapping a backend that declares no locking in JanusGraph's own locker. Session 04 reached the first implementation: a row is a `ConcurrentSkipListMap` entry whose value holds **two arrays** — an `int[]` offset index and one packed `byte[]` — so there are **no `Entry` objects at rest**, a slice is **two binary searches** comparing the query column against a window of raw bytes without materializing anything, and the returned entries **alias the live page** rather than copying it. Lesson 05 read the opposite situation: BerkeleyJE is a flat ordered map with no column dimension at all, so `OrderedKeyValueStoreAdapter` **manufactures one by concatenating the row key onto every column**. Whether that needs a post-filter turns entirely on whether keys are fixed-width — with every key exactly 8 bytes, lexicographic order on `key ‖ column` *is* lexicographic order on the pair, so a prefix range scan is exact; with variable-width keys it is not, and a trailing 2-byte length plus an `equalKey` predicate is the repair. `Backend` hands the fixed `8` — `sizeof(long)` — to exactly three stores **by name** (`edgestore`, its lock store, and the ids store); `graphindex` and everything else pay the variable-length cost. The duplication the whole scheme creates is paid for one line below it, by `dbConfig.setKeyPrefixing(true)`. Lesson 06 closed Part I's first half by answering the question the previous three sessions kept raising — *where would an assertion live?* — and the answer is uncomfortable. The conformance suites are in `janusgraph-backend-testutils/src/**main**/java` and reach backends as an ordinary compile-scope jar, so a whole backend's coverage is **one abstract method**: `getConfiguration()` at the graph level, `openStorageManager()` at the store level, which is why lesson 05's two BerkeleyJE suites differ by one expression. But a backend has **four different ways to turn an inherited test off**, and they are not equivalent: a bare `@Override` removes it silently, `@Disabled` reports a skip, `@Disabled("reason")` reports why — and **`@Test` with an empty body and no `@Disabled` runs, passes, and is counted as coverage**. The in-memory backend passes `JanusGraphTest`'s 229 methods by disabling **31** of them, none with a reason; both BerkeleyJE KCVS suites use the fourth idiom on the two concurrency tests, so four reported passes cover nothing. `@FeatureFlag`, the one *mechanical* capability gate, knows **4 of the 24** feature booleans and fires as a `BeforeTestExecutionCallback` — *after* `@BeforeEach` has already opened two managers and cleared storage. And the sharpest finding is a test this track had already read twice: `BerkeleyVariableLengthKCVSTest.retrieveBackendAndGetKeyValue`, the regression test for lesson 05's variable-key-length leak, wraps the call its own comment marks *"Errors out here without fix"* in a `catch (BackendException)` that rolls back and swallows — **so it passes whether or not the fix is present.** Lesson 07 closed Part I with the wiring: `Backend` is two-phase — the constructor turns `StoreFeatures` into configuration, `initialize` opens **six** named stores, and **three of the six** go through the locking manager, so a backend without innate locking really runs **nine**. The transaction stack is four levels deep (`BackendTransaction` &rarr; `CacheTransaction` &rarr; `ExpectedValueCheckingTransaction` &rarr; two real backend transactions, opened unconditionally) and `unwrapTx` strips exactly one level per wrapper — except in the one `KCVSProxy` method that forgets to call it, which nothing currently reaches. Cache invalidation **does not evict**: it marks the row so reads *bypass* for at least `db-cache-clean-wait` ms, and the sweep that finally drops the stale entries is triggered by a `CountDownLatch(5)` counted down by wasted reads. And the retry backoff every read and write inherits is **a coin flip, not a ±20% jitter** — an `(int)` cast truncates the perturbation divisor to 1 or 2, so a temporarily failing read is retried a measured median of **14** times and as many as **38**, against documentation that promises exponential backoff. Lesson 08 opened Part II on the number everything else is keyed by, and found that there are **two** numbers: the vertex id Gremlin hands back and the row key the backend shards on are different 64-bit words. An id is `[0 | count | partition | 3-bit type suffix]`; one line of `getKey` rebuilds it as `[partition | count | suffix]`, rotating the partition out of the middle of the word and hard against the **top**, so that partitions land in different regions of the key space while consecutive vertices in one partition get keys 8 apart. Id `104` has row key `0xa000000000000008`, and with partition bits in play the key's **sign bit can be set** — which is why the parse path is `>>>` throughout and never `>>`. The partition width is not the 0 the class's own default suggests: `cluster.max-partitions` defaults to **32**, is `FIXED` at graph creation, and its validator forbids 1, so **every real graph runs at 5 partition bits** and the no-arg constructor that would give 0 has no caller in the tree. Each partition bit is paid for out of the vertex-count ceiling, one for one. `VertexIDType` turns out not to be a stored tag at all but a variable-length **suffix code** in the low bits, with the type hierarchy encoded as prefix containment — so every type predicate is one mask, and the fact that the three proper user-vertex suffixes are `000`, `010` and `100` is what makes lesson 07's `EDGESTORE_MAX_KEY` (eight `0xFF` bytes) **unreachable by construction**, which is the only reason that full-scan bound is safe. The lesson also found `fromVertexId` missing the positivity check its documented inverse `toVertexId` has: a pre-commit temporary id passes both of its preconditions — one uses `>>>`, the other compares signed against a positive bound — and comes back as a negative "user id" instead of an exception.

Lesson 09 supplied the two inputs lesson 08 had taken as given — where `count` and `partition` come from — and found that the production default throws four of those sixty-three bits away. Coordination is **amortised, not eliminated**: `StandardIDPool.nextID` is a `synchronized` counter bump over an in-memory block, a background renewal fires when 30% of the block is left (7,000 of 10,000 for vertices, 56,000 of 80,000 for relations), and the only thing that ever talks to storage is a claim protocol that runs **once per 10,000 vertices** on a thread nobody is waiting on. That protocol is a write-wait-read consensus over one row of `janusgraph_ids`: everyone writes a claim unconditionally, waits `ids.authority.wait-time` plus a tenth of it (**330 ms**), reads the row back, and the claim whose column sorts first wins — losers delete their own column, and a delete that fails five times **burns ids but can never duplicate them**, which is the entire reason the scheme is safe over an eventually consistent store. The counter in that column is stored **negated**, so lexicographic column order means newest-claim-first and a five-column slice answers "what is the highest claimed id" on a row holding thousands of historical claims. The row key is lesson 08's rotation one word narrower — the partition shifted hard against the top of a 32-bit int, with the conflict-avoidance tag in the low bits of the same int. **And that tag is the finding.** `ids.authority.conflict-avoidance-tag-bits` defaults to **4**, is `FIXED` at graph creation, and its value defaults to `0` with the mode defaulting to `NONE` — so `getId` returns `count << 4` with a zero tag, **every count JanusGraph assigns is a multiple of 16**, the first user vertex id in a fresh default graph is **4096** rather than 256, consecutive vertices in one partition are 128 apart rather than 8, and **fifteen sixteenths of every namespace's count space is unreachable on every graph anyone has created with the defaults**. Four bits spent on a field nothing uses, unchangeably, in a 63-bit budget the previous lesson had just finished counting. Smaller things: the one message emitted when id allocation finally gives up prints its timeout with `Duration.getNano()`, which is **0** for the 120-second default, so it reads *"Reached timeout 0"*; two contiguity assertions in `IDAuthorityTest` are gated on a tag width of 0 that **none of its three parameterizations uses**, so neither has ever run; a `volatile` timestamp is written on every single id assignment (**33 ns** measured) for a getter with no caller anywhere in the tree; and lesson 08's open question about `count == 0` has a two-character answer — `BASE_ID = 1`, so the authority never offers one, and `addPadding`'s refusal was only ever the second line of defence.

Lesson 10 spent the bits lessons 08 and 09 had only counted. `EdgeSerializer.writeRelation` is 94 lines that turn one in-memory relation into one cell of the row lesson 08 addressed, and it writes **one buffer and returns one integer** — `valuePosition`, the entire boundary between the column the backend sorts on and the value it never interprets. That integer is assigned in six places, and the six are six different storage contracts: a `MANY2ONE` out-edge and a `SINGLE` property get a column consisting of **nothing but the relation-type prefix**, so there is physically one cell per `(vertex, type)` and a second write **overwrites** the first with no read, no lock and no check; a `SET` property puts the value in the column, which is set semantics for free; `MULTI` and `LIST` put the relation id in the column, so nothing is ever overwritten. **The column is the uniqueness constraint.** The same edge therefore produces two columns of two different shapes, one per endpoint row. Everything the reader needs *after* the sort keys — the adjacent vertex id, the relation id — is written **backward**, so a parse walks in from the tail and the variable-width sort-key window in the middle needs no length header; that one trick is also what makes `ADJACENT_ID` and `JANUSGRAPHID` addressable as pseudo-sort-keys by the query builder. A descending vertex-centric index is a **one's complement over exactly the sort-key window** — not the prefix, so a DESC type stays in its band, and not the tail, so tail-reading is order-independent — which is also why the `0xff` missing-value marker correctly sorts last in ASC and, flipped to `0x00`, first in DESC, with the exclusive slice bound landing on the matching side in each case.

Then the finding: **lesson 09's four conflict-avoidance bits cost one byte in every single cell of the database.** The relation-type prefix gets a 1-byte encoding only for a schema count of 7 or less, and the smallest count a default graph can assign is 16 — so the cheapest case in JanusGraph's own variable-length encoding is **unreachable on every graph anyone has created with the defaults**, permanently, because the option is `FIXED`. The 2-byte prefix that every real graph pays instead holds exactly **63** relation types; the 64th spills to three. And the ordering turns out to be weaker than the data model suggests: re-implementing `writePositiveWithPrefix` line-for-line and sweeping five thousand counts finds exactly one inversion, at the byte-length boundary, because the STOP bit marks the **last** byte rather than the first — so at the default stride the 63rd relation type sorts *after* the 64th. **Columns are grouped by relation type, not sorted by relation-type id.** Nothing in the read path depends on the stronger property, and the same STOP bit is why: category bounds compare only the first byte's top three bits, per-type slices are exact byte-prefix matches, and a three-byte prefix can never land inside a two-byte `Direction.BOTH` window. No test asserts any of it — the 1,000,000-trial `IDHandler` loop checks round trips and bounds and never compares two type prefixes to each other. Those top three bits turn out to be a **six-band partition of every row**: system property, system edge, user property, user edge, and two bands for invisible-non-system types that the category-bounds helper **cannot reach**, because it passes the same boolean twice. Those two bands are where every vertex-centric index lives — an index is not an auxiliary structure but a **whole new invisible `MULTI` relation type**, which is why it is invisible (both to stay out of the all-relations slice and because an IN-only unidirected label is otherwise illegal), and why an edge with *N* vertex-centric indexes is **2 + N full columns**, each a complete re-serialization. The lesson also closed three carried questions: `TYPE_LEN_RESERVE` *is* the 3-bit prefix length, `MAX_PADDING_BITWIDTH` *is* the single shift that strips a relation type's padding, and the "conflicting first-bit conventions" between row keys and columns need no reconciling at all — row keys put the partition at the top, columns put the band at the top, and they address different things.

Lesson 11 read lesson 10 backwards. `parseRelation` is the only code in the tree that has to re-derive a relation from bytes with no length headers to help it, and it does so by walking **one cursor** back and forth across a cell rather than streaming it — `valuePosition` serving as both the exclusive end of the column and the *origin* the backward reader counts down from. Two things came out of it. The first answers the question lesson 10 left open and inverts the reason the tail is written backward: `VariableLong`'s backward encoding puts its length in the **first** byte, the mirror image of the forward encoding's stop-bit-on-the-last-byte, and a sweep of 400,000 consecutive values finds **zero order inversions** against the forward encoding's one at every length boundary. The tail ids are written backward so they can be **sorted**, not so they can be read — that is what makes the adjacent vertex id a usable sort-key position — and the price is a hard 3-byte floor that the very first id a default graph assigns already pays: 4096 costs 3 bytes backward against 2 forward, and a default `MULTI` edge is an 8-byte column with an empty value. The second is a gap in a five-week-old fix: a commit from 2026-10-02 stopped JanusGraph re-parsing property-less relations on every property read, by promoting a `null` to a third cache state instead of inferring "did we parse" from "did we find anything" — but the memo it added lives on `EdgeSerializer.readRelation`, and `readRelation` is not on the `RelationReader` interface. The Hadoop/Spark reader holds only a `RelationReader`, so it **fully parses every edgestore column twice per vertex row and caches none of it**, and the first of those two passes needs nothing but the header.

Lesson 12 opened the bytes lessons 10 and 11 had both handed to `serializer` without looking inside, and the finding is a single byte. `StandardSerializer` has four write entry points, and `EdgeSerializer` chooses between them by **where in the column the value is going**, not by what type it is: a private three-valued enum, `InlineType`, with two orthogonal booleans — a sort key gets `writeObjectByteOrder`, a signature key gets `writeObject` with no identifying id because its position implies the key, a remaining property pays an inline relation-type prefix, and a key declared `Object.class` goes through `writeClassAndObject`, which the schema builder structurally confines to the last of those three. Then the finding: **the `0x00` flag byte the dispatcher prepends is load-bearing for *order*, not for null.** `ByteSerializer.writeByteOrder(Byte.MAX_VALUE)` is `putByte((byte)(127 - (-128)))`, which is **the single byte `0xff`** — byte-identical to the missing-value marker lesson 10 found `EdgeSerializer` writing to end an open sort-key range before the relations that have no value of that key. The same collision sits at the top of every fixed-width type: `Short.MAX_VALUE` is `ffff`, `Long.MAX_VALUE` eight `ff`, `Double.NaN` `fff8…`, `new UUID(-1,-1)` sixteen `ff`. Without the flag, a vertex-centric index on a `Byte` sort key would file every relation valued `127` at exactly the column position of every relation with no value at all. That also makes `writesMissingValuesLast`'s odd-looking second clause exact rather than arbitrary — it is really the question *"does the first byte come from the two-valued flag protocol?"* — and the clause exists to exclude **exactly one serializer in the tree**, a private inner `ClassSerializer` which supports null, writes no flag, and encodes null as registration 0, so a `Class` sort key's missing values sort *first*.

The lesson also answered the question lesson 11 had set it, and the answer killed a PR as written. **No in-tree `readObjectByteOrder` is length-ambiguous**: ten of the eleven order-preserving datatypes are fixed-width in byte order, and the eleventh, `String`, is `3 + 2n` and self-delimiting by a `00 00` terminator that its own writer refuses to let into the payload — verified, read length equals write length over twenty thousand strings. So lesson 11's unbounded ASC sort-key read cannot be reached by anything JanusGraph ships, and candidate 20 drops from "silent corruption" to a one-line hardening whose only trigger is a third-party serializer, which the schema builder accepts on nothing stronger than an `instanceof`. Four more things came out of the same reading. **`Date` is order-preserving and `Instant` is not** — so you cannot build a vertex-centric index ordered by the canonical Java timestamp type, while the `sortKey` javadoc's own example is *"a property key with a timestamp data type"*. **`UUIDSerializer` knowingly violates the `OrderPreservingSerializer` contract**, writing two *unbiased* longs so the bytes sort by unsigned bits while `UUID.compareTo` compares each half signed: 10,070 of 20,000 random pairs disagree, which is why `UUID` is absent from the 3,000,000-trial order test and has a separate one — an eight-year-old change justified by "it implements `Comparable`" that took until a commit five weeks ago to finish fixing, and then by changing the *comparators* rather than the bytes. **Enum sort keys are ordered by declaration order and nothing in the format records it**, across seventeen persisted internal enums. And the sort-key premium is **zero for every fixed-width type**, landing entirely on `Integer` (5 bytes against 2 for small values) and `String` (`3 + 2n` against `1 + n`, so `'alice'` is 13 bytes against 6) — in the column, which lesson 10 established a vertex-centric index keeps a second full copy of, in each of two endpoint rows.

Lesson 13 closed Part II by asking where relation types come from, and the answer is that **there is no catalog**. A property key is a vertex in the same `edgestore`, written by the same `EdgeSerializer` and read back by the same `parseRelation`, described entirely by **six** system property keys and **two** system edge labels whose ids are *computed* rather than stored — `(raw << 6) | 37` for a system property key, `| 53` for a system edge label, so `VertexExists` is always 101 and `SchemaName` always 2085 on every instance before a single byte is read. That is the whole bootstrap. `mgmt.makePropertyKey("name").dataType(String.class).make()` lands as **eleven edgestore columns plus two graphindex entries**, and the definition is **exactly seven** of those columns — enforced by set *equality*, not containment, in `TypeDefinitionMap.isValidDefinition` — so one ordinal byte, 5 for `DATATYPE` against 6 for `UNIDIRECTIONAL`, is the entire on-disk difference between a property key and an edge label. Property keys and edge labels deliberately share the `rt` namespace, which is why one storage lookup serves `getPropertyKey` and `getEdgeLabel` both, and why the two kinds can never share a name.

The lesson also settled the two debts it inherited. **Lesson 11's**: `getExistingRelationType` bottoms out at a static seventeen-entry map for system ids, and otherwise at a vertex constructor that chooses `PropertyKeyVertex` against `EdgeLabelVertex` against `JanusGraphSchemaVertex` against `CacheVertex` **from the id's suffix bits alone**, before any byte of the row is read — the stored `SchemaCategory` is there for enumeration, not dispatch. **Lesson 12's**: every `TypeDefinitionCategory` is persisted as its declaration-order **ordinal**, one byte, with no version marker and only a disabled-by-default `assert` standing between a reordered enum and silently reinterpreted schema. *"Don't change the order because it breaks backward compatibility"* is not a style note; the ordinal **is** the on-disk name of a schema field. The sharpest twelve lines in the day's reading are `StandardSchemaCache.isCacheable`, which caches an **empty** definition-edge result but refuses to cache an empty *definition*, because every schema vertex necessarily has one — so an empty answer there means "not visible on this instance yet", not "none".

Lesson 14 opened Part III with the item the syllabus flagged as reference material, and found a mechanism instead. There is no configuration object that merges a file with the database: there is **one row** in the `system_properties` store, row key the UTF-8 bytes of the word `configuration`, columns the dotted option paths, values a one-byte type registration followed by the serializer's bytes &mdash; and the freeze marker, `hidden.frozen`, is a column in that same row, hidden from the option listing only because it fails to parse as an option path and the parse failure is logged at debug. On top of that row sits a three-layer stack of decorators, `MergedConfiguration(overwrite, MixedConfiguration(global, local))`, and **the whole five-constant `ConfigOption.Type` enum reduces, at open time, to two `if`s over three predicates**: `isGlobal()`, `isManaged()`, `isLocal()`. The headline answer is a negative one. `FIXED`, `GLOBAL_OFFLINE` and `GLOBAL` are **indistinguishable while a graph opens**; only two sites in the entire tree read the constant, both after open, and they are what make the three differ &mdash; `ModifiableConfiguration.set`, and `ManagementSystem`'s verifier, which for a `GLOBAL_OFFLINE` change demands that exactly one instance be open, that it be this one, and then marks the graph for shutdown.

The two findings worth carrying are both about things that happen once and are never revisited. **`MASKABLE` options leak from the first instance to every later one**: the first-open copy filters on `isGlobal()`, which includes `MASKABLE`, so whatever that instance's properties file happened to say is frozen into the global row, never refreshed, never discrepancy-checked &mdash; and inherited, silently and with no log line, by any later instance that omits the option, in place of the code default. And **opening a graph creates and destroys an entire storage connection before the real one exists**: the config row has to be readable before the `Backend` can be configured from it, so the builder opens a store manager from the local file alone, reads and freezes the row through it, closes it via try-with-resources, and only then lets `getBackend()` open a second manager and a second reader of the same row. The cost is a double open on every embedded start; the consequence is that any storage option whose authoritative value lives in the row is not applied to the manager that reads the row. The day also mapped the `StandardJanusGraph` constructor as a dependency graph and found one invariant held by sequence alone: the schema cache is wired at line 308, but its retriever opens transactions and would throw `graphShutdown` until `isOpen` is set at line 320. Nothing asserts it and no test pins it.

Lesson 15 answered the question Part III exists to answer: what actually happens in memory when you call `addVertex` or set a property, before anything is persisted. The answer is narrower than it looks. Every data write in JanusGraph funnels through one private method — `connectRelation` — and that method fans out to **three** destinations: each endpoint vertex's own relation container, the transaction's relation container, and the transaction's vertex cache (the last only for endpoints that are *not* new). Properties get a fourth, an index of added properties by key and value that graph-centric queries read. Lose any one of the four and a different thing breaks: lose the per-vertex container and `v.out("knows")` stops seeing uncommitted edges; lose the transaction container and the write is never persisted; lose the cache entry and a vertex evicted under memory pressure comes back as a fresh object with an empty container.

The structural finding is that **the per-transaction and per-vertex relation containers are the same Java class, constructed with opposite arguments** — `SimpleAddedRelations(false)` for the transaction, `SimpleAddedRelations(true)` for each vertex — and that single boolean cascades: at transaction level the property counter is permanently zero, the by-label edge index is never built, and the method that takes a set of relation types to filter on **ignores it entirely**; at vertex level the flat property set is allocated with capacity zero and never written, properties are bucketed by key *name*, and a by-label edge index appears the moment a vertex passes 32 added edges. Alongside it: `ids.flush` defaults to `true`, so a new vertex's temporary id is alive for exactly three statements and nothing ever observes it; `ElementLifeCycle` is a six-state machine in one byte whose three middle states are `private` and whose predicates are range tests on the numeric ordering, with `New` and `Modified` both absorbing; and the transaction's `getAllUnsafe()` — the one view method that is *not* defensively copied — is handed live to the commit path, which is the whole meaning of the name.

Two smaller findings are worth carrying. **Adding an index to a property key silently changes that key's write path**: three conditions gate an optimisation that skips reading the old value entirely and marks the new one `upsert`, and an index breaks all three in one move, with no log line and no metric. And the comment explaining why the vertex cache has a hardcoded 100-element floor cites issue **#893** — which, read at the source, is a 2018 pull request removing Elasticsearch TTL documentation. The hazard the floor mitigates is real (a non-atomic lookup-then-construct sequence that lets two threads of one transaction build two objects for the same vertex), but the floor lowers its probability rather than fixing it, and the citation sends anyone investigating into unrelated history.

Lesson 16 spent lesson 15's three collections, and the syllabus question it was given — *the order deletes and additions are emitted in* — turned out to have an answer one layer below the method that was supposed to decide it. `prepareCommit` is seven phases over three accumulators, and the first four touch storage only to take locks: they collect per-vertex mutations, per-vertex changed properties, and index updates. Phase five then writes the edgestore with **one call per vertex row**, handing that row's additions and deletions to the same call, in one object. So within a row there is no ordering at all — and there does not need to be, because `Mutation.consolidate()` drops any deletion whose **column** matches an addition's, under a rule its own javadoc states: *additions apply logically after deletions*. That is session 02's `KeyColumnValueStore` contract, read off an interface fourteen lessons earlier, finally being spent. It is a stronger design than ordering the writes would be, since it survives a backend that reorders within a batch — and session 03's finding still applies, which is that nothing in the codebase verifies a backend honours it.

Three other things came out of the same reading. **The delete/add lock asymmetry is the uniqueness constraint**: a deletion locks with the full serialized entry, asserting *this cell exists with this content*, while an addition locks with the column alone and a null expected value, asserting *this cell does not exist* — and an addition whose endpoint is a vertex created in the same transaction takes no lock at all, which is why bulk-loading fresh vertices is free of storage locks even with locking consistency configured. **Index failure is swallowed by design**: the commit path collects every index exception into a map, logs each one, flags the transaction `SECONDARY_FAILURE` in its write-ahead log, and returns success — and the repair path needs `tx.log-tx`, which defaults to off and is force-disabled under batch loading, so on a default graph a mixed-index write failure leaves no trace a repair job could use. The upstream issue asking whether that should throw has been open since 2017. And the lesson **corrected lesson 15 about a layer** rather than a fact: the `upsert` flag lesson 15 described as a promise to the commit path is never read there. Its single consumer is `StandardVertexProperty.remove()`, which pays back the slice query the blind-overwrite optimisation skipped, so by the time the commit path sees anything, an upsert-then-remove has already become an ordinary deletion of the old database-resident value.

**Why a bottom-up syllabus.** JanusGraph is a translation layer, so the sequence climbs the translation: the storage contract (`KeyColumnValueStore`, `StoreFeatures`, the in-memory and BerkeleyJE backends) &rarr; graph &harr; bytes (`IDManager`, `VertexIDAssigner`, `EdgeSerializer`, `StandardSerializer`) &rarr; the write path (`StandardJanusGraphTx`, `commit`, `IndexSerializer`, `ConsistentKeyLocker`) &rarr; the read path (vertex caches, the two query builders, `QueryProcessor`) &rarr; Gremlin integration (the optimizer strategies, `JanusGraphStep`) &rarr; schema, mixed indexes and the CQL backend. Reading `StandardJanusGraph.commit` before knowing what a `SliceQuery` promises is how people bounce off this codebase.

## Format

- `README.md`: the track entry — a lesson, or, in a `contributor-reading` track, a reading session. If a lesson is genuinely large, `README.md` becomes a short overview linking numbered sub-documents (`01-<subtopic>.md`, `02-<subtopic>.md`, …) in the same folder; reading sessions are never split.
- `daily-diff.md`: that day's Daily Diff digest.

Every document starts with an `entry-meta` HTML comment (date, type, track, lesson, title, slug). The index below is generated from those blocks. `type` is `lesson`, `reading-session`, `daily-diff`, or `capstone`; a capstone carries `lesson: —` and shows `—` in the `#` column of the index.

A lesson contains, in order:

1. Title and a one-line `date · track · lesson N of T` header
2. **Where This Fits**: previous lesson, what this adds, what it sets up
3. A point-wise breakdown of the real mechanics (headed sections, tables, code; no prose walls)
4. At least one structural Mermaid diagram
5. **Hands-On**: something to run that makes the internals visible, with what to look for
6. **Where This Breaks Down**: limits, costs, and tradeoffs
7. **Further Study**, 8. **Next Steps**, 9. **Sources** (only links verified that day), 10. **Takeaways**

A reading session contains instead: the header line with the pinned short SHA; **From Your Last Notes** (answers to the previous session's open questions, skipped on session 01); **Where This Fits**; **Today's Reading** (the files to open as pinned permalinks, with line ranges and what to skip); **Map**; **Questions To Answer From The Code**; **Hands-On**; **Contribution Radar** (real open upstream issues); **My Notes** (the reader's half); **Sources**.
