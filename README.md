# Daily Learning Log

A daily technical learning log that goes deep. Each entry targets the actual mechanics of a system (storage layouts, wire protocols, scheduler behaviour, failure modes) rather than a feature tour or a summary of marketing pages.

Every lesson is written to be *runnable*: it carries a hands-on exercise you can execute against a real system, at least one structural diagram of the mechanism under discussion, and a source list containing only links that were actually read while writing it.

## How This Works

- **One subject at a time.** The log follows a multi-week *track*: a sequential deep dive into a single database or systems subject. The track's syllabus and progress live in [`TRACK.md`](TRACK.md), which is the single source of truth for what has been taught and what comes next.
- **One lesson per day, each building on the last.** Every day takes the first unchecked lesson from the syllabus. Lessons assume everything earlier in the track is known and open with a *Where This Fits* section linking the previous lesson. Missed days are never backfilled; the track simply continues.
- **Scope is handed forward explicitly.** A comment block in `TRACK.md` records, per lesson, what it took, what it deliberately left for a later lesson, which source commit it read, which measurements reproduced, and which did not. That is what keeps a 33-lesson sequence from re-teaching itself or quietly contradicting an earlier day. `TRACK.md` keeps the notes for the three most recent lessons; older ones roll off into git history, and [`TRACK-ARCHIVE.md`](TRACK-ARCHIVE.md) records the exact commit and blob to read for each lesson range. Nothing is deleted and nothing is duplicated — the lesson documents themselves are the real record. A note records what that run *believed*: on 2026-10-24 lesson 05 found that lesson 04's handover had confidently asserted an identifier that exists in no branch of PostgreSQL, so a specific claim is worth one fetch to check before building on it. On 2026-10-26 the correction ran the other way, against a *measurement* — lesson 06's "59 heap fetches" turned out to be `rows-on-the-dirtied-block + 1` and reproduced as 58.
- **A separate Daily Diff digest every day.** Alongside the lesson, each day folder has a `daily-diff.md` covering an edition of [The Daily Diff](https://tdd.cat/): a point-wise summary plus a deep dive on the single most significant item, with its source link followed and the underlying thing read. A digest covers the newest edition not yet covered, says which one it is, and records how it was found. When no new edition has published, the digest says so explicitly rather than inventing items.

Take the count from the endpoint you took the items from, and say which one that was. Editions are identified by **date**, never by the archive's edition number, which has been observed moving *backwards* between consecutive days (079 for 2026-10-11, then 055 for 2026-10-12).

  **Why any of this happens — a first-party answer, found 2026-10-24.** The front page states: *"Editions are published with a 2-day settling window so the highest-signal discussions and insights surface."* So the front page and the archive are not broken caches drifting at random; they surface the *settled* view, while RSS and the dated permalink can expose an edition before it has settled. That one sentence predicts the lead/lag structure of the whole table above — RSS and the dated pages ahead, front page and archive one to two days behind — and it is why "the cheap endpoints agree" has never been evidence of currency. It does not explain the `client_error` false negatives or the HTML/PDF count split, which remain unexplained caching behaviour.

The next entry is **lesson 09 — The buffer manager: `BufferDesc`, the clock-sweep victim search, and the strategy ring**.

**Measurement is now the norm in this track, and so is saying when it fails.** Lessons 01 and 02 were derived entirely from source constants and said so. Lesson 03 stood up a real PostgreSQL 16.15 cluster with `pageinspect`; lesson 04 did it again and used it to close both of lesson 02's outstanding debts — the page fingerprint `00 20 04 20` at offsets 16–19, and the 8160-byte `MaxHeapTupleSize` ceiling, which reported `row is too big: size 8168, maximum size 8160` at exactly the predicted boundary. **Lesson 05 is the first lesson in which every single number is measured**, and it spends that cluster on three things worth knowing: an `INSERT` landing on a different block before and after `VACUUM`, because the FSM's upper levels are propagated by nothing but `FreeSpaceMapVacuum()`; a row needing exactly 8,136 bytes refusing a block holding exactly 8,136 bytes, so the relation extended — eight bytes of rounding costing one 8 KB page; and `MaxHeapTuplesPerPage` = 291 observed directly, three lessons after it was derived.

**Lesson 06 is the first to cross an auxiliary fork's page boundary.** A 35,000-block heap put the visibility map's second page exactly where `HEAPBLOCKS_PER_PAGE = 32,672` says it should be, with heap block 32,671's bit pair landing on byte **8,191** — the last byte of the page — and block 32,672's on byte 24 of the next. The same table confirmed lesson 05's FSM arithmetic independently (11 FSM pages for the same heap: nine bottom plus two upper levels). It also produced the measurement the track will keep citing: **one `UPDATE` cost 59 heap fetches**, fully accounted for as 57 live rows on the dirtied block plus one dead index entry plus one on the block the new version landed on. The same `Index Only Scan` node did 20,000 fetches, then 0, then 59, with no replan — so "index-only" is a plan shape, not a promise. And `pg_waldump` priced the thing lesson 05's FSM gets for free: **59 bytes of WAL per page marked all-visible**, 980 records and 5.65% of one 16 MB segment.

**Lesson 07 answers lesson 06's cliff, and corrects it.** Heap-Only Tuples are the mechanism that stops an `UPDATE` from clearing a second visibility-map bit and adding an index entry, and the lesson measures both ends of it. The steady-state result is the one worth remembering: **2,000 autocommitted single-row updates produced zero blocks of heap growth, zero blocks of index growth, zero dead tuples, and no `VACUUM` ever ran** — the row oscillating forever between two recycled line pointers behind one `LP_REDIRECT` root, visible verbatim in `pg_waldump` as `redirected: [11->41]` then `redirected: [11->43]`. The lesson also pins the prune heuristic experimentally to within one row: a page holding a known-prunable dead tuple with **888 free bytes (10.84%) survived three consecutive full table scans unchanged**, and one extra `INSERT` taking it to 484 bytes caused the very next scan to prune — which locates `Max(fillfactor slack, BLCKSZ/10)` by observation rather than by reading it. And it establishes the fact that `lp_off` **changes units**: in an `LP_REDIRECT` line pointer it is an `OffsetNumber`, not a byte offset, proved by a measured value of `19` that is inside the 24-byte page header and therefore cannot be an offset into the page.

**The correction runs the other way this time, against lesson 06.** Lesson 07 rebuilt lesson 06's index-only-scan experiment and reproduced its geometry exactly — 863 heap blocks, `shared hit=57`, the new version landing on block 862 — but measured **58** heap fetches where lesson 06 measured 59, because its table holds 57 rows on block 0 rather than 58. The figure is `rows-on-the-dirtied-block + 1`, not a constant, and the track now says so rather than carrying 59 forward. The honest reading of HOT's cost follows the same discipline: its own `Heap2/PRUNE` records are **36.7% of its WAL bill** at 61 bytes apiece, so against a cold-update workload whose `Btree/INSERT_LEAF` records are 51.7% of *its* bill, HOT saves 1.49× — 166 WAL bytes per update against 247 — and not the order of magnitude the feature's reputation suggests. What it does save outright is growth: zero blocks against ten. And one idle `REPEATABLE READ` transaction in another session destroys all of it, turning 2,000 updates into 35 new heap blocks and 2,000 dead tuples **while still reporting 98.25% HOT** — which makes the HOT-update ratio a misleading health metric and the table size the honest one.

**Lesson 08 goes under the floor every earlier lesson stood on, and most of it is `strace`.** `smgr.c` is a function-pointer table with one row and `md.c` is that row; together they are where the 1 GB segment boundary, the relation-extension batching and the durability handoff to the checkpointer actually live. Four measurements are worth carrying forward. **A 142,858-block relation is measured in exactly two `lseek`s**: `lseek(fd, 0, SEEK_END)` on segment 0 returns `1073741824`, which equals `RELSEG_SIZE` and is therefore the loop's signal to open `base/16388/16438.1`, whose `lseek` returns 11,786 blocks — and the same call repeated three seconds later in the same backend, because `smgr_cached_nblocks` is deliberately ignored outside recovery for want of shared invalidation. **How you insert decides your syscall count by 60×**: the same 20,000 rows cost **2,860 single-block `pwritev`s** through `INSERT … SELECT` and **48 `fallocate`s** through `COPY`, whose lengths ramp `10, 10, 20, 40, 64, 64, …` — `bistate->already_extended_by` accumulating against a `MAX_BUFFERS_TO_EXTEND_BY` of 64, observed as a series rather than inferred. **The fsync queue's economics are its key**: `FileTag` is `(handler, forknum, rlocator, segno)`, so roughly **40,800 block writes collapsed into 21 `fsync` calls** at the next checkpoint (≈1,940:1), with a relation's heap and its `_fsm` fork as *separate* entries and `pg_xact/0000` riding the same queue — and `sync files=N` in `checkpoint complete` turns out to be literally the number of hash entries processed. And **`skipFsync=true` is a transfer of obligation, not a waiver**: four plain `CREATE TABLE t (id int, pad text)` statements produced four synchronous `fsync`s in the user's own backend, on `pg_toast_*_index` relfilenodes, because `nbtsort.c` builds btrees outside shared buffers and must pay its own debt in `smgrimmedsync()`.

**Lesson 08 also adds two findings that run against expectation, and one experiment that failed.** The `file_extend_method` GUC changes the syscall and not the clock: `posix_fallocate` versus `write_zeros` showed **no wall-time difference across five `COPY` runs each** (medians 638 ms and 670 ms), only ~11% more bytes charged to the backend in `/proc/<pid>/io` and a different syscall shape — `pwritev` with `iovcnt` capped at `PG_IOV_MAX = 32`, so a 64-block extension splits 32 + 32. And bulk extension can be switched off by a setting nobody associates with it: at `shared_buffers = 128kB` with `max_connections = 100`, `LimitAdditionalPins()` computes `NBuffers / max_backends`, floors it at 1, and the identical `COPY` that made 48 `fallocate` calls made **2,861 one-block `pwritev`s** instead — extension batching is a function of `shared_buffers` divided by `max_connections`, documented nowhere a DBA would look. The failure is recorded as a failure: the attempt to force `buffers_backend_fsync > 0` by `SIGSTOP`ping the checkpointer **deadlocked on `max_wal_size`** instead, so the queue-full fallback in `register_dirty_segment()` was read in the source and never executed. The honest reason the counter stayed at zero in every configuration — including 57,987 backend writes against a 16-slot queue — is that `CompactCheckpointerRequestQueue()` collapses duplicates, and the failure mode needs a queue both full *and* duplicate-free.

Honest null results are recorded rather than smoothed over. Lesson 04's was the `attcacheoff` cliff, real in `TupleDescFinalize()` and **not** reproducible as a measurable cost at ten columns. Lesson 05 has two. The predicted `PageGetHeapFreeSpace() == 0` trap at the 291-tuple ceiling **did not fire** — free line pointers defeat it, so that ceiling is not a cause of FSM under-reporting but of unreclaimable line-pointer space, 1,152 bytes of it decided only by *which* of 291 rows you keep. And lesson 04's handover asserted a `HEAP_FSM_CREATION_THRESHOLD` of four pages that **exists in no branch of PostgreSQL**: the patch introducing it was reverted in 2019 and never re-landed. **Why PostgreSQL after SQLite.** The SQLite capstone identified four tradeoffs the whole engine rests on — catalog placement, writer concurrency, cost-model resolution, and the verification oracle — and PostgreSQL resolves every one of them the opposite way: a catalog of real tables rather than a b-tree inside page 1, many concurrent writers with per-tuple visibility rather than one writer and three file locks, a floating-point cost model rather than a 10-bit `10·log₂` channel, and no `integrity_check` at all (the nearest equivalent, `amcheck`, is an extension and checks only indexes). Those four are the intended comparison axes for the whole track. Lesson 01 already paid the first one's bill: `pg_class.relfilenode` is `0` for `pg_class` itself, so the catalog cannot describe its own storage. Lesson 02 opened a fifth thread that runs alongside them — PostgreSQL systematically removes *redundancy* that SQLite keeps as a cross-check. SQLite's page header stores an explicit cell count beside its cell pointer array; PostgreSQL derives the count as `(pd_lower − 24) / 4`, and so has nothing to check it against. Lesson 03 carried that thread into the record format and found the sharper version of it: PostgreSQL's tuple header carries no type information whatsoever, so a heap page cannot be decoded without `pg_class` and `pg_attribute`, where SQLite's varint record header makes every page self-describing. Lesson 04 pushed it one step further and found the limit case: the 18-byte on-disk TOAST pointer carries two OIDs — `va_valueid` and `va_toastrelid`, both cross-checked against the catalog — and no length and no type of its own, so a salvaged page yields `t_hoff`, then eighteen opaque bytes pointing at a relation you can no longer name. Lesson 05 found the thread's cheerful inverse: the Free Space Map is *deliberately* allowed to be wrong — not WAL-logged, written with `MarkBufferDirtyHint()`, read with `RBM_ZERO_ON_ERROR`, repaired by three separate self-correcting checks — because being wrong about free space costs disk, not correctness. It also retired a reading of lesson 02 that was becoming load-bearing: bytes 16–19 are `00 20 04 20` on an **FSM** page too, so that fingerprint identifies *zero special space*, not *heap*. Lesson 06 found the thread's other pole and it is the sharpest statement of the comparison so far: the visibility map is *the same shape of fork* as the FSM — one flat array in lesson 02's hole, read with `RBM_ZERO_ON_ERROR`, a page that `bufpage.c` thinks is empty — and it is **WAL-logged while the FSM is not**, because its bit exists in two places at once. `PD_ALL_VISIBLE` on the heap page and the bit in the map are one truth stored twice, and PostgreSQL 16's own header comment says why that forces a WAL record: *"When we set a visibility map during VACUUM, we must write WAL. This may seem counterintuitive, since the bit is basically a hint."* So the project's willingness to let a derived structure be wrong is not a style; it is priced per structure, against what being wrong costs. Being wrong about free space costs disk; being wrong about visibility costs correct answers. Lesson 05 and lesson 06 are the same design decision taken twice, with opposite results. Lesson 07 extends the thread to the heap itself: a `LP_REDIRECT` line pointer has `lp_len = 0` and an `lp_off` that silently changes units, with `lp_flags` as the only discriminator and nothing to cross-check it against — the same removed redundancy, now in the two bits that decide how to read the other thirty. Lesson 08 finds the thread's structural limit: **PostgreSQL does not store a relation's size anywhere.** SQLite keeps the database page count in the header at offset 28 and validates it against the change counter; PostgreSQL derives relation size by `lseek(SEEK_END)` on the segment files every time it is asked, keeps a cache field it refuses to trust outside recovery, and says in `smgr.h` why — *"there is no cache invalidation for fork extension"*. The in-memory segment map is explicitly not a census either: `md.c`'s header comment warns that *"a fork's `md_num_open_segs` having a specific value does not necessarily mean the relation doesn't have additional segments"*, because another backend can extend the relation while this one isn't looking. The filesystem is the only authority on how big a table is.
