# Daily Learning Log

A daily technical learning log that goes deep. Each entry targets the actual mechanics of a system (storage layouts, wire protocols, scheduler behaviour, failure modes) rather than a feature tour or a summary of marketing pages.

Every lesson is written to be *runnable*: it carries a hands-on exercise you can execute against a real system, at least one structural diagram of the mechanism under discussion, and a source list containing only links that were actually read while writing it.

## How This Works

- **One subject at a time.** The log follows a multi-week *track*: a sequential deep dive into a single database or systems subject. The track's syllabus and progress live in [`TRACK.md`](TRACK.md), which is the single source of truth for what has been taught and what comes next.
- **One lesson per day, each building on the last.** Every day takes the first unchecked lesson from the syllabus. Lessons assume everything earlier in the track is known and open with a *Where This Fits* section linking the previous lesson. Missed days are never backfilled; the track simply continues.
- **Scope is handed forward explicitly.** A comment block in `TRACK.md` records, per lesson, what it took, what it deliberately left for a later lesson, which source commit it read, which measurements reproduced, and which did not. That is what keeps a 33-lesson sequence from re-teaching itself or quietly contradicting an earlier day. `TRACK.md` keeps the notes for the three most recent lessons; older ones roll off into git history, and [`TRACK-ARCHIVE.md`](TRACK-ARCHIVE.md) records the exact commit and blob to read for each lesson range. Nothing is deleted and nothing is duplicated — the lesson documents themselves are the real record. A note records what that run *believed*: on 2026-10-24 lesson 05 found that lesson 04's handover had confidently asserted an identifier that exists in no branch of PostgreSQL, so a specific claim is worth one fetch to check before building on it. On 2026-10-26 the correction ran the other way, against a *measurement* — lesson 06's "59 heap fetches" turned out to be `rows-on-the-dirtied-block + 1` and reproduced as 58. On 2026-11-04 a third kind of correction appeared: lesson 05's handover had described the in-memory backend as "unordered", and `InMemoryStoreManager` declares **both** scan shapes, so a loose adjective in a note is worth one re-read too. On 2026-11-07 a fourth: lesson 08's handover said `count == 0` is unreachable because `addPadding` forbids it, which is true but is the *second* line of defence — `BASE_ID = 1` means the id authority never offers a zero count at all. A correct claim can still be the wrong reason. On 2026-11-08 a fifth, and the most useful kind: two lessons had *accounted* for `TYPE_LEN_RESERVE` and `MAX_PADDING_BITWIDTH` without spending them, and a note that says "owed to lesson N" is what made the third lesson go looking — the constants turned out to be the column prefix's 3 bits and its one shift, and the "conflicting conventions" the earlier note flagged needed no reconciling at all. On 2026-11-09 a sixth, and it ran against an *explanation* rather than a fact: two lessons had recorded that the relation ids and adjacent vertex ids at the tail of a column are written backward *so that a parse can walk in from the end*, which is true and is not the reason — the backward encoding is the only order-preserving one in the package, and the tail is written that way so it can be used as a sort key. A note that explains a mechanism correctly can still have the causality backwards.
- **A separate Daily Diff digest every day.** Alongside the lesson, each day folder has a `daily-diff.md` covering an edition of [The Daily Diff](https://tdd.cat/): a point-wise summary plus a deep dive on the single most significant item, with its source link followed and the underlying thing read. A digest covers the newest edition not yet covered, says which one it is, and records how it was found. When no new edition has published, the digest says so explicitly rather than inventing items.

Lesson 10 spent the bits lessons 08 and 09 had only counted. `EdgeSerializer.writeRelation` is 94 lines that turn one in-memory relation into one cell of the row lesson 08 addressed, and it writes **one buffer and returns one integer** — `valuePosition`, the entire boundary between the column the backend sorts on and the value it never interprets. That integer is assigned in six places, and the six are six different storage contracts: a `MANY2ONE` out-edge and a `SINGLE` property get a column consisting of **nothing but the relation-type prefix**, so there is physically one cell per `(vertex, type)` and a second write **overwrites** the first with no read, no lock and no check; a `SET` property puts the value in the column, which is set semantics for free; `MULTI` and `LIST` put the relation id in the column, so nothing is ever overwritten. **The column is the uniqueness constraint.** The same edge therefore produces two columns of two different shapes, one per endpoint row. Everything the reader needs *after* the sort keys — the adjacent vertex id, the relation id — is written **backward**, so a parse walks in from the tail and the variable-width sort-key window in the middle needs no length header; that one trick is also what makes `ADJACENT_ID` and `JANUSGRAPHID` addressable as pseudo-sort-keys by the query builder. A descending vertex-centric index is a **one's complement over exactly the sort-key window** — not the prefix, so a DESC type stays in its band, and not the tail, so tail-reading is order-independent — which is also why the `0xff` missing-value marker correctly sorts last in ASC and, flipped to `0x00`, first in DESC, with the exclusive slice bound landing on the matching side in each case.

Then the finding: **lesson 09's four conflict-avoidance bits cost one byte in every single cell of the database.** The relation-type prefix gets a 1-byte encoding only for a schema count of 7 or less, and the smallest count a default graph can assign is 16 — so the cheapest case in JanusGraph's own variable-length encoding is **unreachable on every graph anyone has created with the defaults**, permanently, because the option is `FIXED`. The 2-byte prefix that every real graph pays instead holds exactly **63** relation types; the 64th spills to three. And the ordering turns out to be weaker than the data model suggests: re-implementing `writePositiveWithPrefix` line-for-line and sweeping five thousand counts finds exactly one inversion, at the byte-length boundary, because the STOP bit marks the **last** byte rather than the first — so at the default stride the 63rd relation type sorts *after* the 64th. **Columns are grouped by relation type, not sorted by relation-type id.** Nothing in the read path depends on the stronger property, and the same STOP bit is why: category bounds compare only the first byte's top three bits, per-type slices are exact byte-prefix matches, and a three-byte prefix can never land inside a two-byte `Direction.BOTH` window. No test asserts any of it — the 1,000,000-trial `IDHandler` loop checks round trips and bounds and never compares two type prefixes to each other. Those top three bits turn out to be a **six-band partition of every row**: system property, system edge, user property, user edge, and two bands for invisible-non-system types that the category-bounds helper **cannot reach**, because it passes the same boolean twice. Those two bands are where every vertex-centric index lives — an index is not an auxiliary structure but a **whole new invisible `MULTI` relation type**, which is why it is invisible (both to stay out of the all-relations slice and because an IN-only unidirected label is otherwise illegal), and why an edge with *N* vertex-centric indexes is **2 + N full columns**, each a complete re-serialization. The second is a gap in a five-week-old fix: a commit from 2026-10-02 stopped JanusGraph re-parsing property-less relations on every property read, by promoting a `null` to a third cache state instead of inferring "did we parse" from "did we find anything" — but the memo it added lives on `EdgeSerializer.readRelation`, and `readRelation` is not on the `RelationReader` interface. The Hadoop/Spark reader holds only a `RelationReader`, so it **fully parses every edgestore column twice per vertex row and caches none of it**, and the first of those two passes needs nothing but the header.

Lesson 12 opened the bytes lessons 10 and 11 had both handed to `serializer` without looking inside, and the finding is a single byte. `StandardSerializer` has four write entry points, and `EdgeSerializer` chooses between them by **where in the column the value is going**, not by what type it is: a private three-valued enum, `InlineType`, with two orthogonal booleans — a sort key gets `writeObjectByteOrder`, a signature key gets `writeObject` with no identifying id because its position implies the key, a remaining property pays an inline relation-type prefix, and a key declared `Object.class` goes through `writeClassAndObject`, which the schema builder structurally confines to the last of those three. Then the finding: **the `0x00` flag byte the dispatcher prepends is load-bearing for *order*, not for null.** `ByteSerializer.writeByteOrder(Byte.MAX_VALUE)` is `putByte((byte)(127 - (-128)))`, which is **the single byte `0xff`** — byte-identical to the missing-value marker lesson 10 found `EdgeSerializer` writing to end an open sort-key range before the relations that have no value of that key. The same collision sits at the top of every fixed-width type: `Short.MAX_VALUE` is `ffff`, `Long.MAX_VALUE` eight `ff`, `Double.NaN` `fff8…`, `new UUID(-1,-1)` sixteen `ff`. Without the flag, a vertex-centric index on a `Byte` sort key would file every relation valued `127` at exactly the column position of every relation with no value at all. That also makes `writesMissingValuesLast`'s odd-looking second clause exact rather than arbitrary — it is really the question *"does the first byte come from the two-valued flag protocol?"* — and the clause exists to exclude **exactly one serializer in the tree**, a private inner `ClassSerializer` which supports null, writes no flag, and encodes null as registration 0, so a `Class` sort key's missing values sort *first*.

The lesson also answered the question lesson 11 had set it, and the answer killed a PR as written. **No in-tree `readObjectByteOrder` is length-ambiguous**: ten of the eleven order-preserving datatypes are fixed-width in byte order, and the eleventh, `String`, is `3 + 2n` and self-delimiting by a `00 00` terminator that its own writer refuses to let into the payload — verified, read length equals write length over twenty thousand strings. So lesson 11's unbounded ASC sort-key read cannot be reached by anything JanusGraph ships, and candidate 20 drops from "silent corruption" to a one-line hardening whose only trigger is a third-party serializer, which the schema builder accepts on nothing stronger than an `instanceof`. Four more things came out of the same reading. **`Date` is order-preserving and `Instant` is not** — so you cannot build a vertex-centric index ordered by the canonical Java timestamp type, while the `sortKey` javadoc's own example is *"a property key with a timestamp data type"*. **`UUIDSerializer` knowingly violates the `OrderPreservingSerializer` contract**, writing two *unbiased* longs so the bytes sort by unsigned bits while `UUID.compareTo` compares each half signed: 10,070 of 20,000 random pairs disagree, which is why `UUID` is absent from the 3,000,000-trial order test and has a separate one — an eight-year-old change justified by "it implements `Comparable`" that took until a commit five weeks ago to finish fixing, and then by changing the *comparators* rather than the bytes. **Enum sort keys are ordered by declaration order and nothing in the format records it**, across seventeen persisted internal enums. And the sort-key premium is **zero for every fixed-width type**, landing entirely on `Integer` (5 bytes against 2 for small values) and `String` (`3 + 2n` against `1 + n`, so `'alice'` is 13 bytes against 6) — in the column, which lesson 10 established a vertex-centric index keeps a second full copy of, in each of two endpoint rows.

**Why a bottom-up syllabus.** JanusGraph is a translation layer, so the sequence climbs the translation: the storage contract (`KeyColumnValueStore`, `StoreFeatures`, the in-memory and BerkeleyJE backends) &rarr; graph &harr; bytes (`IDManager`, `VertexIDAssigner`, `EdgeSerializer`, `StandardSerializer`) &rarr; the write path (`StandardJanusGraphTx`, `commit`, `IndexSerializer`, `ConsistentKeyLocker`) &rarr; the read path (vertex caches, the two query builders, `QueryProcessor`) &rarr; Gremlin integration (the optimizer strategies, `JanusGraphStep`) &rarr; schema, mixed indexes and the CQL backend. Reading `StandardJanusGraph.commit` before knowing what a `SliceQuery` promises is how people bounce off this codebase.
