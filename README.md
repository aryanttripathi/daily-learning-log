# Daily Learning Log

A daily technical learning log that goes deep. Each entry targets the actual mechanics of a system (storage layouts, wire protocols, scheduler behaviour, failure modes) rather than a feature tour or a summary of marketing pages.

Every lesson is written to be *runnable*: it carries a hands-on exercise you can execute against a real system, at least one structural diagram of the mechanism under discussion, and a source list containing only links that were actually read while writing it.

## How This Works

- **One subject at a time.** The log follows a multi-week *track*: a sequential deep dive into a single database or systems subject. The track's syllabus and progress live in [`TRACK.md`](TRACK.md), which is the single source of truth for what has been taught and what comes next. For a long track, the append-only registers — PR candidates found along the way, and the ledger of open questions with the lesson that owns each — live beside it under [`tracks/`](tracks/); the JanusGraph track's PR candidates are in [`tracks/janusgraph-registers.md`](tracks/janusgraph-registers.md) (volume 1, candidates 1–64, frozen on 2026-11-22) and [`tracks/janusgraph-registers-2.md`](tracks/janusgraph-registers-2.md) (volume 2, candidates 65 on), with numbering continuous across the two.
- **One lesson per day, each building on the last.** Every day takes the first unchecked lesson from the syllabus. Lessons assume everything earlier in the track is known and open with a *Where This Fits* section linking the previous lesson. Missed days are never backfilled; the track simply continues.
- **Scope is handed forward explicitly.** A comment block in `TRACK.md` records, per lesson, what it took, what it deliberately left for a later lesson, which source commit it read, which measurements reproduced, and which did not. That is what keeps a long sequence from re-teaching itself or quietly contradicting an earlier day. `TRACK.md` keeps the notes for the three most recent lessons; older ones roll off into git history, and [`TRACK-ARCHIVE.md`](TRACK-ARCHIVE.md) records the exact commit and blob to read for each lesson range. Nothing is deleted and nothing is duplicated — the lesson documents themselves are the real record.

  A note records what that run *believed*, which is why the corrections are worth keeping a list of. On 2026-10-24 lesson 05 found that lesson 04's handover had confidently asserted an identifier that exists in no branch of PostgreSQL, so a specific claim is worth one fetch to check before building on it. On 2026-10-26 the correction ran the other way, against a *measurement* — lesson 06's "59 heap fetches" turned out to be `rows-on-the-dirtied-block + 1` and reproduced as 58. On 2026-11-04 a third kind: lesson 05's handover had described the in-memory backend as "unordered", and `InMemoryStoreManager` declares **both** scan shapes, so a loose adjective in a note is worth one re-read too. On 2026-11-07 a fourth: lesson 08's handover said `count == 0` is unreachable because `addPadding` forbids it, which is true but is the *second* line of defence — `BASE_ID = 1` means the id authority never offers a zero count at all. A correct claim can still be the wrong reason. On 2026-11-08 a fifth, and the most useful kind: two lessons had *accounted* for `TYPE_LEN_RESERVE` and `MAX_PADDING_BITWIDTH` without spending them, and a note that says "owed to lesson N" is what made the third lesson go looking. On 2026-11-09 a sixth, against an *explanation* rather than a fact: two lessons had recorded that the tail ids of a column are written backward *so that a parse can walk in from the end*, which is true and is not the reason — the backward encoding is the only order-preserving one in the package, and the tail is written that way so it can be used as a sort key. On 2026-11-11 a seventh, which closed a debt rather than correcting one: three separate lessons had written down *obligations* for lesson 13, and all three were discharged in one reading. On 2026-11-12 an eighth, the plainest kind: lesson 13's note had listed `attributes.custom.*` as a `FIXED` option, and it is `GLOBAL_OFFLINE`. On 2026-11-14 a ninth, and it is about a mechanism's *layer* rather than its content: lesson 15 had recorded that a property write's `upsert` flag "promises the commit path that a later delete must read the database", and lesson 16 found that the commit path never reads the flag at all — its single consumer is `StandardVertexProperty.remove()`, one layer up. On 2026-11-15 a tenth, and the mildest: lesson 16's "phases 1-4 touch storage only to take locks" is true of three of those four phases and false of the third, which issues slice queries from a parallel stream — a *refinement*, logged as one rather than dressed up as a correction. On 2026-11-16 an eleventh, and the first that corrected a *method* rather than a fact: lesson 17 had handed lesson 18 a falsifiable conjecture **and** a reproduction recipe, and the conjecture turned out to be right while the recipe could not have worked — it named BerkeleyJE, which advertises `locking(true)` and therefore never runs the locking code the conjecture is about. A note can be correct about *what* to check and wrong about *where*, and the second error is the expensive one, because it fails silently as a passing exercise. A handover note is not only a correction channel; it is what makes a lesson arrive with questions instead of a blank page.
- **A separate Daily Diff digest every day.** Alongside the lesson, each day folder has a `daily-diff.md` covering an edition of [The Daily Diff](https://tdd.cat/): a point-wise summary plus a deep dive on the single most significant item, with its source link followed and the underlying thing read. A digest covers the newest edition not yet covered, says which one it is, and records how it was found. When no new edition has published, the digest says so explicitly rather than inventing items.

  **tdd.cat's endpoints are independently cached and disagree with each other, and thirty consecutive runs produced thirty different lead/lag patterns.** The front page, [`/md`](https://tdd.cat/md), the dated `https://tdd.cat/{YYYY-MM-DD}.md` permalink, the dated `https://tdd.cat/{YYYY-MM-DD}/` page, [`/archive/`](https://tdd.cat/archive/), [RSS](https://tdd.cat/rss.xml) and the per-edition PDF have each been observed leading, lagging, failing or disagreeing while the others worked. **The procedure, as it stands after the 2026-11-16 amendment:**

  1. Fetch the front page and [`/archive/`](https://tdd.cat/archive/) and take the **maximum** date either names. A *larger* archive maximum is a reason to probe that date; a *smaller* one is no reason to doubt the front page (2026-11-05).
  2. **Then probe `https://tdd.cat/{today}/` and `https://tdd.cat/{yesterday}/` directly**, because a published edition can be absent from *both* indexes while they agree with each other (2026-11-13, and again 2026-11-15). Try the no-slash form too — the trailing slash is part of the cache key and the two forms have disagreed in one run (2026-10-28).
  3. **Check the `TRACK.md` session log in both directions** before concluding anything: a floor, so a run does not re-digest the edition the previous entry covered (2026-11-07), and a ceiling, so it does not skip an uncovered one by invoking the fallback mechanically (2026-11-09).
  4. **Fallback, last resort only:** if the newest available edition is one a previous entry already digested and no newer edition exists, state the gap with timestamps and endpoints checked, then go deep on **one item from that edition the previous digest did not cover**, saying in the document that that is what is happening (2026-11-08).
  5. Identify editions by **date**, never by the archive's edition number, which has been observed moving backwards. Take the item count from the endpoint you took the items from and say which one that was — the HTML and PDF renderings of one edition have disagreed 43 against 33 (2026-10-24). Edition size carries no information about completeness (2026-11-10). A large edition's page can exceed the ~100 KB one WebFetch returns, so its tail needs a second call with an offset (2026-11-11, used for real on 2026-11-13).
  6. **If the best item in an edition cannot be verified, pick another and say why** (2026-11-15). XRAID was the most on-topic item in the 2026-11-14 edition and both of its primary sources — the mailing-list archive and the author's slides — are robots-disallowed, with the secondary report stating outright that it does not describe the mechanism. A digest says that and deep-dives something it could actually read, rather than filling the gap with plausible generalities.

- **Tracks end with a capstone.** When every lesson is checked, that day's document is a capstone assembling the whole system end to end. The subject moves to *Completed Subjects* in `TRACK.md`, and a new track begins.
- **Some tracks are reading sessions, not lessons.** A track whose `mode` is `contributor-reading` targets a codebase the reader intends to contribute to. Those entries do not explain the code; they point at the exact files to open at a pinned commit, give the minimum map needed to read them efficiently, pose questions whose answers are in the code, and list live upstream issues the reading touches. The other half of each entry is a **`## My Notes`** section written by the reader, and the next session opens by answering the open questions left there. An entry whose `My Notes` stays empty did not count, and the next run says so. **A track can change mode mid-flight**, and the JanusGraph track did on 2026-11-03: a reading-session track whose `My Notes` stays empty for several consecutive sessions is generating guides nobody reads, so the mode flips to `lesson` and the entries start answering their own questions. Entries keep whatever shape they shipped with; the mode only governs what comes next.

## Format

Day folders live at `YYYY/MM/YYYY-MM-DD-<slug>/`:

- `README.md`: the track entry — a lesson, or, in a `contributor-reading` track, a reading session. If a lesson is genuinely large, `README.md` becomes a short overview linking numbered sub-documents (`01-<subtopic>.md`, `02-<subtopic>.md`, …) in the same folder; reading sessions are never split.
- `daily-diff.md`: that day's Daily Diff digest.

Every document starts with an `entry-meta` HTML comment (date, type, track, lesson, title, slug). The index below is generated from those blocks. `type` is `lesson`, `reading-session`, `daily-diff`, or `capstone`; a capstone carries `lesson: —` and shows `—` in the `#` column of the index.

A lesson contains, in order:

1. Title and a one-line `date · track · lesson N of T` header
2. **Where This Fits**: previous lesson, what this adds, what it sets up
3. A point-wise breakdown of the real mechanics (headed sections, tables, code; no prose walls)
4. At least one structural Mermaid diagram
5. **Hands-On**: something to run that makes the internals visible, with what to look for
6. **Where This Breaks Down**: limits, costs, and tradeoffs
7. **Further Study**, 8. **Next Steps**, 9. **Sources** (only links verified that day), 10. **Takeaways**

A reading session contains instead: the header line with the pinned short SHA; **From Your Last Notes** (answers to the previous session's open questions, skipped on session 01); **Where This Fits**; **Today's Reading** (the files to open as pinned permalinks, with line ranges and what to skip); **Map**; **Questions To Answer From The Code**; **Hands-On**; **Contribution Radar** (real open upstream issues); **My Notes** (the reader's half); **Sources**. It carries no *Where This Breaks Down*, *Further Study*, *Next Steps* or *Takeaways* — those would be the entry doing the reader's thinking for him.

Entries before 2026-09-16 predate the track model. They came from a five-slot topic rotation (Database Internals, System Design / Paper Analysis, Tech Blog Analysis, The Daily Diff Digest, Variety) and are kept in the index as history.
