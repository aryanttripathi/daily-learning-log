# Daily Learning Log

A daily technical learning log that goes deep. Each entry targets the actual mechanics of a system (storage layouts, wire protocols, scheduler behaviour, failure modes) rather than a feature tour or a summary of marketing pages.

Every lesson is written to be *runnable*: it carries a hands-on exercise you can execute against a real system, at least one structural diagram of the mechanism under discussion, and a source list containing only links that were actually read while writing it.

## How This Works

- **One subject at a time.** The log follows a multi-week *track*: a sequential deep dive into a single database or systems subject. The track's syllabus and progress live in [`TRACK.md`](TRACK.md), which is the single source of truth for what has been taught and what comes next.
- **One lesson per day, each building on the last.** Every day takes the first unchecked lesson from the syllabus. Lessons assume everything earlier in the track is known and open with a *Where This Fits* section linking the previous lesson. Missed days are never backfilled; the track simply continues.
- **Scope is handed forward explicitly.** A comment block in `TRACK.md` records, per lesson, what it took, what it deliberately left for a later lesson, which source commit it read, which measurements reproduced, and which did not. That is what keeps a 33-lesson sequence from re-teaching itself or quietly contradicting an earlier day. `TRACK.md` keeps the notes for the three most recent lessons; older ones roll off into git history, and [`TRACK-ARCHIVE.md`](TRACK-ARCHIVE.md) records the exact commit and blob to read for each lesson range. Nothing is deleted and nothing is duplicated — the lesson documents themselves are the real record. A note records what that run *believed*: on 2026-10-24 lesson 05 found that lesson 04's handover had confidently asserted an identifier that exists in no branch of PostgreSQL, so a specific claim is worth one fetch to check before building on it. On 2026-10-26 the correction ran the other way, against a *measurement* — lesson 06's "59 heap fetches" turned out to be `rows-on-the-dirtied-block + 1` and reproduced as 58.
- **A separate Daily Diff digest every day.** Alongside the lesson, each day folder has a `daily-diff.md` covering an edition of [The Daily Diff](https://tdd.cat/): a point-wise summary plus a deep dive on the single most significant item, with its source link followed and the underlying thing read. A digest covers the newest edition not yet covered, says which one it is, and records how it was found. When no new edition has published, the digest says so explicitly rather than inventing items.

**Pinned source.** Every line number and permalink in this track reads `JanusGraph/janusgraph` at commit `a59ae8d8` (2026-10-28), re-pinned only at a syllabus Part boundary. Session 01 established the premise the other 27 sessions depend on: a vertex is a **row**, its incident edges and properties are that row's **cells sorted by column**, each edge is stored **twice** (once per endpoint row), and the maximum cells per row in a backend is therefore the maximum vertex degree JanusGraph can support on it. The supernode problem is a line of the data model, not a bug. Session 02 opened the contract those rows are read through: the column interval is **half-open**, `[sliceStart, sliceEnd)`, so asking for one exact column means asking for `[point, point+1)`; a `mutate` applies its **deletions strictly before its additions**, so a column in both lists survives with the new value; and a lock taken with `acquireLock` is **only verified on the transaction's first `mutate`**, which makes locking here discretionary rather than immediate.

**Why a bottom-up syllabus.** JanusGraph is a translation layer, so the sequence climbs the translation: the storage contract (`KeyColumnValueStore`, `StoreFeatures`, the in-memory and BerkeleyJE backends) → graph &harr; bytes (`IDManager`, `EdgeSerializer`, `StandardSerializer`) → the write path (`StandardJanusGraphTx`, `commit`, `IndexSerializer`, `ConsistentKeyLocker`) → the read path (vertex caches, the two query builders, `QueryProcessor`) → Gremlin integration (the optimizer strategies, `JanusGraphStep`) → schema, mixed indexes and the CQL backend. Reading `StandardJanusGraph.commit` before knowing what a `SliceQuery` promises is how people bounce off this codebase.

## Format

Day folders live at `YYYY/MM/YYYY-MM-DD-<slug>/`:

- `README.md`: the track entry — a lesson, or, in a `contributor-reading` track, a reading session. If a lesson is genuinely large, `README.md` becomes a short overview linking numbered sub-documents (`01-<subtopic>.md`, `02-<subtopic>.md`, …) in the same folder; reading sessions are never split.
- `daily-diff.md`: that day's Daily Diff digest.

Every document starts with an `entry-meta` HTML comment (date, type, track, lesson, title, slug). The index below is generated from those blocks. `type` is `lesson`, `reading-session`, `daily-diff`, or `capstone`; a capstone carries `lesson: —` and shows `—` in the `#` column of the index.

A lesson contains, in order:

1. Title and a one-line `date · track · lesson N of T` header
2. **Where This Fits**: previous lesson, what this adds, what it sets up
3. A point-wise breakdown of the real mechanics (headed sections, tables, code; no prose walls)
4. At least one structural Mermaid diagram
5. **Hands-On**: something to run that makes the internals visible, with what to look for
6. **Where This Breaks Down**: limits, costs, and tradeoffs
7. **Further Study**, 8. **Next Steps**, 9. **Sources** (only links verified that day), 10. **Takeaways**

A reading session contains instead: the header line with the pinned short SHA; **From Your Last Notes** (answers to the previous session's open questions, skipped on session 01); **Where This Fits**; **Today's Reading** (the files to open as pinned permalinks, with line ranges and what to skip); **Map**; **Questions To Answer From The Code**; **Hands-On**; **Contribution Radar** (real open upstream issues); **My Notes** (the reader's half); **Sources**. It carries no *Where This Breaks Down*, *Further Study*, *Next Steps* or *Takeaways* — those would be the entry doing the reader's thinking for him.

Entries before 2026-09-16 predate the track model. They came from a five-slot topic rotation (Database Internals, System Design / Paper Analysis, Tech Blog Analysis, The Daily Diff Digest, Variety) and are kept in the index as history.
