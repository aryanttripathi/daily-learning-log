# Daily Learning Log

A daily technical learning log that goes deep. Each entry targets the actual mechanics of a system (storage layouts, wire protocols, scheduler behaviour, failure modes) rather than a feature tour or a summary of marketing pages.

Every lesson is written to be *runnable*: it carries a hands-on exercise you can execute against a real system, at least one structural diagram of the mechanism under discussion, and a source list containing only links that were actually read while writing it.

## How This Works

- **One subject at a time.** The log follows a multi-week *track*: a sequential deep dive into a single database or systems subject. The track's syllabus and progress live in [`TRACK.md`](TRACK.md), which is the single source of truth for what has been taught and what comes next.
- **One lesson per day, each building on the last.** Every day takes the first unchecked lesson from the syllabus. Lessons assume everything earlier in the track is known and open with a *Where This Fits* section linking the previous lesson. Missed days are never backfilled; the track simply continues.
- **Scope is handed forward explicitly.** A comment block in `TRACK.md` records, per lesson, what it took, what it deliberately left for a later lesson, which source commit it read, which measurements reproduced, and which did not. That is what keeps a 33-lesson sequence from re-teaching itself or quietly contradicting an earlier day. `TRACK.md` keeps the notes for the three most recent lessons; older ones roll off into git history, and [`TRACK-ARCHIVE.md`](TRACK-ARCHIVE.md) records the exact commit and blob to read for each lesson range. Nothing is deleted and nothing is duplicated — the lesson documents themselves are the real record.
- **A separate Daily Diff digest every day.** Alongside the lesson, each day folder has a `daily-diff.md` covering an edition of [The Daily Diff](https://tdd.cat/): a point-wise summary plus a deep dive on the single most significant item, with its source link followed and the underlying thing read. A digest covers the newest edition not yet covered, says which one it is, and records how it was found. When no new edition has published, the digest says so explicitly rather than inventing items.

  **tdd.cat's endpoints are independently cached and disagree with each other, in a different pattern on each of twelve consecutive days.** The front page, [`/md`](https://tdd.cat/md) (the documented "latest edition" endpoint), the dated `https://tdd.cat/{YYYY-MM-DD}.md` permalink, the dated `https://tdd.cat/{YYYY-MM-DD}/` page, [`/archive/`](https://tdd.cat/archive/) and [RSS](https://tdd.cat/rss.xml) have each been observed leading, lagging or failing while the others worked. ([`llms.txt`](https://tdd.cat/llms.txt) is the source for the endpoint list.) The observation log:

  So the procedure is: **try the dated `https://tdd.cat/{date}.md` permalink first**, for today and the previous day or two, because it is the only endpoint never observed to report an edition that does not exist — and the only one that has never *missed* one. Then try RSS, the cheapest endpoint that has ever agreed with the permalink (10-18 and 10-21, including on the story count). Use [`/archive/`](https://tdd.cat/archive/) only as a *lower* bound on what exists and never as an upper one: a date appearing there unlinked means nothing, as 2026-10-21 established — though on 2026-10-22 the archive was current and its unlinked date *did* correspond to a missing edition, which is exactly why it is a lower bound and not a test. The trailing-slash `https://tdd.cat/{date}/` page has failed on six consecutive observations and is no longer tried. Cross-check the item count against any other endpoint that answers, recording explicitly when no second endpoint serves that edition, as happened on 2026-10-15, 2026-10-17 and 2026-10-19. Editions are identified by **date**, never by the archive's edition number, which has been observed to move *backwards* between consecutive days (079 for 2026-10-11, then 055 for 2026-10-12); item counts vary *wildly* — 30, 26, 18, 21, **3**, then **35** on six consecutive days, and 39, 36, 40 on the three most recent — which is why the count is cross-checked against a second endpoint whenever one is available before a short edition is reported as short.
- **Tracks end with a capstone.** When every lesson is checked, that day's document is a capstone assembling the whole system end to end. The subject moves to *Completed Subjects* in `TRACK.md`, and a new track begins.

## Current Track

**PostgreSQL Internals**: **Lesson 3 of 35** · lesson 03 shipped 2026-10-22 · [syllabus and progress &rarr;](TRACK.md)

The next entry is **lesson 04 — Attribute storage: MAXALIGN padding between attributes, 1-byte vs 4-byte varlena headers, `atthasmissing`, and TOAST**.

**Lesson 03 is the first entry in this track with measured numbers in it.** Lessons 01 and 02 were derived entirely from source constants and said so; lesson 03 stood up a real PostgreSQL 16.15 cluster with `pageinspect` and observed the struct byte by byte, so every figure marked *measured* in it was seen rather than computed. The recipe is recorded in [`TRACK.md`](TRACK.md) so later lessons can do the same.

The syllabus runs in seven parts, ordered by PostgreSQL's actual source layout rather than a textbook outline: Part I physical storage and the heap (`access/heap`, `storage/page`, `storage/smgr`), Part II shared-memory buffers and locks (`storage/buffer`, `storage/lmgr`), Part III MVCC and transaction management (`access/transam`), Part IV isolation (`README-SSI`), Part V WAL, recovery and replication, Part VI access methods (`access/nbtree`, the index AM interface), Part VII planner and executor. It was built from the chapter list of [Part VII Internals](https://www.postgresql.org/docs/current/internals.html) plus the set of in-tree design READMEs in `postgres/postgres@45fc51fc` — which are the files where the project writes down how each module actually works, and which are the backbone of the track.

**Why PostgreSQL after SQLite.** The SQLite capstone identified four tradeoffs the whole engine rests on — catalog placement, writer concurrency, cost-model resolution, and the verification oracle — and PostgreSQL resolves every one of them the opposite way: a catalog of real tables rather than a b-tree inside page 1, many concurrent writers with per-tuple visibility rather than one writer and three file locks, a floating-point cost model rather than a 10-bit `10·log₂` channel, and no `integrity_check` at all (the nearest equivalent, `amcheck`, is an extension and checks only indexes). Those four are the intended comparison axes for the whole track. Lesson 01 already paid the first one's bill: `pg_class.relfilenode` is `0` for `pg_class` itself, so the catalog cannot describe its own storage. Lesson 02 opened a fifth thread that runs alongside them — PostgreSQL systematically removes *redundancy* that SQLite keeps as a cross-check. SQLite's page header stores an explicit cell count beside its cell pointer array; PostgreSQL derives the count as `(pd_lower − 24) / 4`, and so has nothing to check it against. Lesson 03 carried that thread into the record format and found the sharper version of it: PostgreSQL's tuple header carries no type information whatsoever, so a heap page cannot be decoded without `pg_class` and `pg_attribute`, where SQLite's varint record header makes every page self-describing.

## Format

Day folders live at `YYYY/MM/YYYY-MM-DD-<slug>/`:

- `README.md`: the track lesson. If a lesson is genuinely large, `README.md` becomes a short overview linking numbered sub-documents (`01-<subtopic>.md`, `02-<subtopic>.md`, …) in the same folder.
- `daily-diff.md`: that day's Daily Diff digest.

Every document starts with an `entry-meta` HTML comment (date, type, track, lesson, title, slug). The index below is generated from those blocks. `type` is `lesson`, `daily-diff`, or `capstone`; a capstone carries `lesson: —` and shows `—` in the `#` column of the index.

A lesson contains, in order:

1. Title and a one-line `date · track · lesson N of T` header
2. **Where This Fits**: previous lesson, what this adds, what it sets up
3. A point-wise breakdown of the real mechanics (headed sections, tables, code; no prose walls)
4. At least one structural Mermaid diagram
5. **Hands-On**: something to run that makes the internals visible, with what to look for
6. **Where This Breaks Down**: limits, costs, and tradeoffs
7. **Further Study**, 8. **Next Steps**, 9. **Sources** (only links verified that day), 10. **Takeaways**

Entries before 2026-09-16 predate the track model. They came from a five-slot topic rotation (Database Internals, System Design / Paper Analysis, Tech Blog Analysis, The Daily Diff Digest, Variety) and are kept in the index as history.
