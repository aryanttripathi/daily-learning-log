# Daily Learning Log

A daily technical learning log that goes deep. Each entry targets the actual mechanics of a system (storage layouts, wire protocols, scheduler behaviour, failure modes) rather than a feature tour or a summary of marketing pages.

Every lesson is written to be *runnable*: it carries a hands-on exercise you can execute against a real system, at least one structural diagram of the mechanism under discussion, and a source list containing only links that were actually read while writing it.

## How This Works

- **One subject at a time.** The log follows a multi-week *track*: a sequential deep dive into a single database or systems subject. The track's syllabus and progress live in [`TRACK.md`](TRACK.md), which is the single source of truth for what has been taught and what comes next. For a long track, the append-only registers — PR candidates found along the way, and the ledger of open questions with the lesson that owns each — live beside it under [`tracks/`](tracks/); the JanusGraph track's are in [`tracks/janusgraph-registers.md`](tracks/janusgraph-registers.md).
- **One lesson per day, each building on the last.** Every day takes the first unchecked lesson from the syllabus. Lessons assume everything earlier in the track is known and open with a *Where This Fits* section linking the previous lesson. Missed days are never backfilled; the track simply continues.
- **Scope is handed forward explicitly.** A comment block in `TRACK.md` records, per lesson, what it took, what it deliberately left for a later lesson, which source commit it read, which measurements reproduced, and which did not. That is what keeps a long sequence from re-teaching itself or quietly contradicting an earlier day. `TRACK.md` keeps the notes for the three most recent lessons; older ones roll off into git history, and [`TRACK-ARCHIVE.md`](TRACK-ARCHIVE.md) records the exact commit and blob to read for each lesson range. Nothing is deleted and nothing is duplicated — the lesson documents themselves are the real record.

In one paragraph: **sessions 01–07 established the storage contract.** A vertex is a *row*, its incident edges and properties are that row's *cells sorted by column*, and each edge is stored twice, once per endpoint row — so a backend's maximum cells per row is the maximum vertex degree JanusGraph supports on it. The column interval is half-open; a `mutate` applies deletions strictly before additions; a lock taken with `acquireLock` is only verified on the transaction's first `mutate`. The 24 `StoreFeatures` booleans a backend declares about itself are enforced by **one** `checkArgument` in the whole tree, and `Backend` reads `locking` *inverted*. The in-memory store keeps a row as two arrays — an `int[]` offset index over one packed `byte[]` — so there are no `Entry` objects at rest and a slice is two binary searches; BerkeleyJE has no column dimension at all and `OrderedKeyValueStoreAdapter` manufactures one by concatenating the row key onto every column, which is exact only for fixed-width keys. The conformance suites ship from `src/main/java` and a backend has four inequivalent ways to switch an inherited test off, one of which — `@Test` with an empty body — *passes and is counted as coverage*. **Lessons 08–13 established graph ⇄ bytes.** The vertex id Gremlin returns and the row key the backend shards on are different 64-bit words, and one line of `getKey` rotates the partition hard against the top of the key; `cluster.max-partitions` defaults to 32, so every real graph runs at 5 partition bits. Ids are allocated from in-memory blocks claimed by a write-wait-read consensus over one row of `janusgraph_ids` that runs once per 10,000 vertices, and the default 4 conflict-avoidance bits — with a tag value of `0` and mode `NONE` — make every assigned count a multiple of 16 and cost one byte in every cell of the database. `EdgeSerializer.writeRelation` writes one buffer and returns one integer, `valuePosition`, and **the column is the uniqueness constraint**: a `MANY2ONE` edge or `SINGLE` property gets a column of nothing but the type prefix, so a second write overwrites with no read and no lock. Everything after the sort keys is written backward so a parse can walk in from the tail with no length headers; a descending vertex-centric index is a one's complement over exactly the sort-key window. There is no type catalog — a property key is a vertex in the same `edgestore`, described by six system property keys and two system edge labels whose ids are computed rather than stored. **Lessons 14–17 established the write path.** `GraphDatabaseConfiguration` merges a properties file with *one row* of `system_properties` keyed by the UTF-8 bytes of the word `configuration`; every data write funnels through `connectRelation` and fans out to three destinations; `prepareCommit` is seven phases over three accumulators; and the composite-index write path makes two byte-layout decisions whose only job is to stop you doing what the storage layer would otherwise allow — a row key that cannot be range-scanned, and a column width that *is* the uniqueness level. In one line: **the two planners are the same kind of function and a different shape** — `GraphCentricQueryBuilder` consults no statistics either, but solves a **weighted set cover** with a lexicographic objective (more clauses covered, then *fewer* indexes, then higher score) behind a swappable `IndexSelectionStrategy` SPI; **a composite index is all-or-nothing**, so one range clause drops it out of candidacy; **the full scan is not a decision but an empty `JointIndexQuery`**, with `query.force-index` the switch that turns it into an exception; and **only the first subquery streams**, every other index in a joint query being materialised in full and unbounded before the first result exists.

Lesson 22 closed Part IV by opening the consumer of both compilers, and the answer is that **`QueryProcessor` is a generic right fold over sub-queries that in the shipped tree almost never folds anything.** What is load-bearing is a three-layer limit discipline, and the fact to keep is the **ordering**: reading outward from the backend, the stack is `executor.execute` → `LimitAdjustingIterator` (counts raw backend results) → the transaction's new-element filter → the `isDeleted`/`matches` filter → the merge fold → `ResultSetIterator` (counts elements emitted). **The in-memory filter sits between the backend limit and the element count**, which is why `limit(10)` bounds what you *receive* and not what is *read*: when the filter eats results the backend limit **doubles** — `L, 2L, 4L …`, with a full re-read each time because there is no cursor — until ten survive or the index runs out. There is no cost ceiling on an unfitted query and no error, only latency that grows with the inverse of the uncovered clause's selectivity. Resuming that re-read needed a whole interface: an iterator that drops results cannot be resumed by element count, because a relation removed between the two reads shifts the window, so `BackendLimitAware` changes the unit of resumption to **backend results** — which makes graph-centric re-reads skip and vertex-centric ones replay every element already seen. **The second finding is what is absent: `QueryProcessor` creates no profiler span at all.** It passes profilers through and never calls `addNested`, `startTimer` or `setResultSize`, so merge time, in-memory sort time and filter time are invisible in `.profile()` *and* in Metrics; the only external traces of in-memory work are the gap between a `backend-query` span's result count — which is *ids read*, not elements emitted — and what the traversal returned, and repeated sibling `backend-query` spans with doubling `limit` annotations. That is the single biggest obstacle to diagnosing a slow JanusGraph query from outside, and it is three missing lines rather than a wrong one. Third, **half the class is dead**: `VertexCentricQuery.isSorted()` is an unconditional `true` and `GraphCentricQuery.numSubQueries()` a literal `1`, so the unsorted branch's multi-sub-query `concat` arm is unreachable and the duplicate-filtering merge the javadoc documents cannot be triggered by any shipped query. And fourth, the common case — a single fitted sorted slice — bypasses the class entirely via `useSimpleQueryProcessor`. Two smaller mechanisms worth remembering: the new-element sort is a bounded top-*k* heap with an explicit stability tie-break, so `limit(10)` and `limit(20)` in one transaction agree on the first ten; and an ordered query whose index cannot sort falls into a **per-sub-query million-element pre-sort budget** that ignores `query.hard-max-limit` and throws rather than truncating. Lesson 23 opened Part V one layer above both compilers, and the finding is that **the content of the strategy layer is not any single rewrite but the dependency graph between twelve strategies — two of which declare no ordering at all.** One `static` block in `StandardJanusGraph` registers all twelve, every one of them a `ProviderOptimizationStrategy` (including `JanusGraphIoRegistrationStrategy`, whose whole job is configuring an `IoStep`), and OLAP gets exactly one of them. Reading the full `applyPrior`/`applyPost` graph produces the fact Part V turns on: **`JanusGraphStepStrategy` and `JanusGraphLocalQueryOptimizerStrategy` have no direct ordering edge**, and the only paths between them run through the two mixed-index aggregation strategies that any user can disable with one `withoutStrategies(...)` call. The second finding is practical enough to change how you write Gremlin against JanusGraph: **`local()` is the only construct that gets an order or a range to the storage layer.** A top-level `out()` folds in a `has()` only when it returns edges, folds no order and no range — the in-source reason is *"We cannot fold in orders or ranges since they are not local"* — and folds only a *high* limit hint without removing the range step; `local(__.outE().has(…).order().by(k).limit(n))` folds condition, order and limit into one vertex-centric slice and then deletes the `local()` wrapper entirely. A vertex-centric query folds **at most one** order key; a graph-centric one folds any number. Third, `or()` turns out to be compiled twice over: each branch is flattened into a list of conditions — with an `order().by(k)` inside a branch becoming `has(k, neq(null))`, because TinkerPop drops elements whose `by()` yields nothing — and then run either as one disjunctive query or as **N separate queries merged inside the step** by `MultiDistinct*Iterator`, which is the positive answer to lesson 22's question about unreachable code: the de-duplicating multi-query merge lives one layer above `QueryProcessor`, so the generic version inside it is dead by design and the right contribution is a comment. Fourth, and the reportable defect of the run: **a traversal that ends in an aggregation is compiled during strategy application, under `QueryProfiler.NO_OP`, and the result is memoized on the step** — `JanusGraphMixedIndexAggStep`'s constructor probes `buildGlobalGraphCentricQuery()` and the strategy then discards the new step when no mixed index can answer it, leaving `g.V().has(k,v).count().profile()` with no compile span at all and index selection already done. Three layers in a row now share one failure mode: a missing index becomes a silent full scan (lesson 21), an unfitted query silently doubles its backend limit (lesson 22), and a fold that stops matching silently does not happen (lesson 23). None raises an error and none is visible in `.profile()`. Four PR candidates logged (61–64), bringing the register to 64.

**Why a bottom-up syllabus.** JanusGraph is a translation layer, so the sequence climbs the translation: the storage contract (`KeyColumnValueStore`, `StoreFeatures`, the in-memory and BerkeleyJE backends) &rarr; graph &harr; bytes (`IDManager`, `VertexIDAssigner`, `EdgeSerializer`, `StandardSerializer`) &rarr; the write path (`StandardJanusGraphTx`, `commit`, `IndexSerializer`, `ConsistentKeyLocker`) &rarr; the read path (vertex caches, the two query builders, `QueryProcessor`) &rarr; Gremlin integration (the optimizer strategies, `JanusGraphStep`) &rarr; schema, mixed indexes and the CQL backend. Reading `StandardJanusGraph.commit` before knowing what a `SliceQuery` promises is how people bounce off this codebase.
